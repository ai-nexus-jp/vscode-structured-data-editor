# 開発指示書：VS Code Structured Data Editor

## 1. エージェントへの依頼

あなたは、VS Code拡張機能、TypeScript、Webview、データ形式変換に精通したシニアソフトウェアエンジニアです。

このリポジトリに、CSV・JSON・Markdownなどの構造化データをVS Code上でプレビューし、表形式で編集し、元のファイルへ安全に反映できる拡張機能を実装してください。

単に設計案やサンプルコードを提示するだけでなく、現在のリポジトリを調査し、実装、テスト、ビルド、ドキュメント更新まで実行してください。既存コードがある場合は、まず内容と状態を確認し、不要な上書きを避けてください。

環境やツールの制約により実行できない作業があれば、その事実を明記し、実行したふりをしないでください。

## 2. 製品ビジョン

### 2.1 目的

AIが読み取りやすいテキストベースのファイル形式を維持しながら、人間がExcelのように直感的にデータを編集できるVS Code拡張機能を提供する。

### 2.2 想定するユーザー体験

- CSV、JSON、MarkdownなどのファイルをVS Codeで開く。
- コマンドまたはエディタ操作からビジュアル編集画面を開く。
- プレビュー上でセルや行・列を編集する。
- 編集内容を元のファイル形式で保存する。
- 必要に応じて別形式（CSV、JSON、Markdown）へエクスポートする。
- Gitの差分管理やAIコーディングツールでの利用を妨げない、標準的で読みやすいテキストファイルを維持する。

### 2.3 製品方針

- 最初はMarkdownテーブル編集を確実に実装する。
- 将来CSV・JSON・TSVなどを追加できるアーキテクチャにする。
- フォーマットごとの読み込み・書き出し処理と、共通編集UIを分離する。
- 初期版で不要な複雑性を持ち込まない。
- データを失う可能性のある変換や保存は、明示的な警告または確認を行う。

## 3. 製品名・リポジトリ

推奨リポジトリ名：`vscode-structured-data-editor`

仮の拡張機能表示名：`Structured Data Editor`

仮のコマンド名：
- `Structured Data Editor: Edit Table Visually`
- 将来追加：`Structured Data Editor: Export As...`

名前の使用可能性は未確認のため、公開前にGitHubとVS Code Marketplaceで確認する。拡張機能のpublisher IDやMarketplace登録情報を捏造・仮定して公開設定しないこと。

## 4. 開発フェーズとスコープ

### Phase 1：Markdownテーブル編集（必須）

- Markdownファイル内で、カーソルが標準的なMarkdownテーブル内にあるときにコマンドを実行できる。
- 対象テーブルを検出し、Webview上に表形式で表示する。
- セル内容を編集できる。
- 行の追加・削除ができる。
- 列の追加・削除ができる。
- Applyで変更を元のMarkdownファイルの該当テーブルに反映する。
- Cancelで変更を破棄する。
- テーブル以外の見出し・文章・コードブロックなどを変更しない。
- 適用前に対象文書の変更を検出し、競合があれば上書きせず、再読み込みまたはキャンセルを促す。
- Markdownを読みやすく整形して出力する。
- Markdownパーサー／シリアライザーの単体テストを作成する。

### Phase 2：CSV対応（将来拡張を考慮して設計）

Phase 1の完成後に実装する。エージェントはPhase 1を優先し、Phase 2を未実装のまま完了扱いにしないこと。

- CSVをグリッドで表示・編集する。
- 元のCSVを同形式で保存する。
- 区切り文字、引用符、セル内カンマ、改行、空セルを正しく扱う。
- 文字コードやBOMを可能な範囲で保持する。
- CSVの列数が不揃いな場合は、データを黙って切り捨てず、検出・警告する。

### Phase 3：JSON対応（将来拡張を考慮して設計）

- 初期対応対象は「オブジェクトの配列」とする。例：
  `[{ "id": 1, "name": "Alice" }, { "id": 2, "name": "Bob" }]`
- 数値、文字列、真偽値、nullの型を不必要に変えない。
- 列の存在しないオブジェクトや、キーの不一致を適切に扱う。
- ネストしたオブジェクトや配列は、初期対応では読み取り専用表示、JSON文字列としての保持、または編集対象外とするなど、情報損失のない方針を明示する。
- 一般的なJSONオブジェクト全体を、意味を失う形で無理に表形式へ変換しない。

### Phase 4：形式変換

- CSV、JSON、Markdown間のエクスポートを追加する。
- 「元ファイルの保存」と「別形式へのエクスポート」を明確に分ける。
- エクスポート先はユーザーが選択する。
- 情報が失われる変換では、実行前に警告する。
- Markdownへの変換では、対象範囲・ヘッダー・列順序を明示する。

### Phase 5：一般公開準備

- テスト、README、CHANGELOG、LICENSE、CONTRIBUTINGなどを整備する。
- CIでlint、型チェック、テスト、ビルドを実行する。
- VS Code Marketplace公開に必要なmanifest情報やパッケージングを確認する。
- publisher ID、トークン、認証情報などをコードやリポジトリに含めない。
- 公開はユーザーの明示的な承認なしに実行しない。

## 5. UX要件

### 5.1 Markdown編集フロー

1. ユーザーがMarkdownファイルを開く。
2. 標準Markdownテーブル内にカーソルを置く。
3. Command Paletteから `Structured Data Editor: Edit Table Visually` を実行する。
4. 編集画面を開き、対象テーブルを表示する。
5. ユーザーがセル、行、列を編集する。
6. Applyで元のMarkdownの該当範囲を置き換える。
7. Cancelでは元ファイルを変更しない。

テーブル外でコマンドを実行した場合、分かりやすいメッセージを表示し、ファイルを変更しない。

### 5.2 編集UI

Phase 1の最低限の機能：
- セルのインライン編集
- 行の追加・削除
- 列の追加・削除
- Apply
- Cancel
- 変更状態の分かる表示
- 横に長い表への対応
- 空セル・空文字列の扱い

コピー＆ペースト、キーボード操作、Undo/Redoの拡張は、MVPの基本動作を安定させた後に追加する。

### 5.3 自動更新と保存方針

製品全体では「プレビュー上で編集すると内部状態が更新される」ことを基本とする。

ただしPhase 1では、要件どおりApplyを明示的な確定操作とする。Apply前に元ファイルを変更しない。Apply後はVS Codeの文書編集APIを利用して該当範囲だけを書き換え、通常の保存フローに従う。

Phase 2以降の元ファイル更新も、まずは編集状態をメモリ上で更新し、保存操作でディスクに反映する設計とする。別形式への出力は別の明示的操作にする。

## 6. アーキテクチャ要件

### 6.1 方針

フォーマット別アダプターと共通の編集モデルを分離する。

想定構成：
- VS Code Extension Host：コマンド登録、文書アクセス、競合検出、適用処理
- Webview：プレビュー・編集UI
- Format Adapters：Markdown、CSV、JSONの解析とシリアライズ
- Shared Data Model：共通の行列データと形式固有メタデータ
- Tests：解析・生成・競合検出・編集操作のテスト

### 6.3 技術選定

基本候補：
- TypeScript
- VS Code Extension API
- VS Code Webview
- React + TypeScript、または初期段階で十分な単純HTML/CSS/JavaScript
- esbuild
- Vitest
- 必要に応じて、信頼できるMarkdownパーサーやCSVパーサー

実際の依存関係は現行の安定バージョンを確認して選定する。依存を追加する場合は、その必要性を説明し、ライセンスも確認する。単純なPhase 1のためだけに過剰な依存を導入しない。

## 7. 共通データモデル

将来の共通モデルは、例えば次のような形を出発点とする。これは簡略例であり、実際の要件に応じて型安全に設計すること。

```typescript
type SourceFormat = "markdown" | "csv" | "json";

interface TabularDocument {
  sourceFormat: SourceFormat;
  columns: Array<{
    id: string;
    name: string;
    type?: string;
  }>;
  rows: Array<Record<string, unknown>>;
  metadata?: Record<string, unknown>;
}
```

注意事項：
- Markdownは文書全体ではなく、対象テーブルとその元の範囲を保持する。
- Markdown内のテーブル以外の内容を破壊しない。
- CSVの区切り文字、引用符、BOMなど、書き戻しに必要な情報を必要に応じてメタデータとして保持する。
- JSONの型やネスト構造を不用意に文字列化しない。
- 表形式にできないデータを、無警告で損失のある形式に変換しない。

## 8. Markdownの解析・シリアライズ要件

Phase 1では、GitHub Flavored Markdownの一般的なパイプ区切りテーブルを対象とする。

最低限考慮する事項：
- ヘッダー行
- 区切り行
- データ行
- 左寄せ・中央寄せ・右寄せの配置指定
- 空セル
- セル内のパイプ文字のエスケープ
- 先頭・末尾のパイプの有無
- 行ごとの列数の不一致
- テーブル直後の通常文章
- コードフェンス内に見えるパイプ表を誤検出しないこと

初期版で対応できない構文がある場合は、黙ってデータを壊すのではなく、テーブルを編集対象として開く前に分かりやすく拒否する。

適用時は元のテーブルの範囲だけを更新する。周辺の見出し、本文、リスト、コードブロック、空行などを無関係に再整形しない。

## 9. 競合と安全性

- Webviewを開いた時点で元テーブルの内容と範囲を記録する。
- Apply時に、元の対象範囲が開いた時点から変更されていないか確認する。
- 競合があれば自動で上書きせず、ユーザーに再読み込みまたはキャンセルを促す。
- 文書が閉じられた、対象範囲が消えた、ファイルが別の内容に置き換わった場合も安全に失敗する。
- 適用失敗時に成功メッセージを出さない。
- Webviewメッセージの型と内容を検証する。
- WebviewのContent Security Policyを設定し、必要なスクリプト・スタイルのみ許可する。
- 不必要なネットワークアクセスや外部送信を行わない。
- 秘密情報やユーザーデータをログに出さない。

## 10. テスト要件

少なくとも次の単体テストを用意する。

### Markdown parser / serializer
- 通常のテーブルを正しく解析・生成できる
- 空セルを保持できる
- 列配置指定を保持できる
- セル内のパイプを安全に扱える、または未対応として拒否できる
- 列数の不一致を検出できる
- コードフェンス内のテーブル風文字列を誤検出しない
- テーブル前後の文書を変更しない
- 空のデータ行を適切に扱う

### Extension / Apply
- カーソルがテーブル内なら編集画面を開く
- カーソルがテーブル外なら文書を変更しない
- Applyで対象テーブルだけを更新する
- Cancelでは文書を変更しない
- 競合時に上書きしない
- 不正なWebviewメッセージで文書を変更しない

可能であれば、代表的なMarkdownサンプルをfixtureとして保存し、テストに利用する。

## 11. 完了条件（Definition of Done）

Phase 1を完了とする条件：

1. 拡張機能がビルドできる。
2. VS CodeのExtension Development Hostで起動できる。
3. Markdownテーブル内のコマンド実行で編集UIが開く。
4. セル、行、列を編集できる。
5. Applyで対象テーブルだけが更新される。
6. Cancelでファイルが変更されない。
7. 競合時に危険な上書きをしない。
8. テストが成功する。
9. READMEにセットアップ、実行、使い方、既知の制約を記載する。
10. 未実装のCSV/JSON機能を、対応済みとして表示しない。
11. lint、型チェック、テスト、ビルドの結果を報告する。
12. 実行できなかった検証があれば、理由と残課題を報告する。

## 12. 開発手順

次の順序で進める。

1. リポジトリの現状、既存コード、package.json、Git状態を確認する。
2. 不明点や破壊的変更のリスクを整理する。
3. Phase 1の最小設計を確定する。
4. Markdownのパーサー・シリアライザーと単体テストを先に実装する。
5. VS CodeコマンドとWebviewを実装する。
6. Apply/Cancelと競合検出を実装する。
7. UIと編集処理を統合する。
8. lint、型チェック、テスト、ビルドを実行する。
9. 失敗を修正して再実行する。
10. README、CHANGELOG、既知の制約を更新する。
11. 最終報告で、変更ファイル、実装済み機能、実行したコマンド、テスト結果、未対応項目を明記する。

各段階で、既存のユーザー変更を無断で破棄しない。依存の大幅変更やファイル削除など影響の大きい判断が必要な場合は、先に説明する。

## 14. 最初に着手すること

まずリポジトリを調査し、現状に合わせた短い実装計画を作成してください。その後、ユーザーの確認待ちで停止する必要がない限り、Phase 1の実装を開始してください。

ただし、既存データの破壊、認証情報の使用、外部への公開・リリースなど、不可逆または外部に影響する操作は、明示的な承認なしに実行しないでください。
